# Совместная работа над первой версией

Подтверждено заказчиком 12.10.2026. GitHub issues с исполнителями и метками достаточно; Projects не требуется. Последнее уточнение разрешает агенту автоматически занимать выбранную свободную задачу от имени своего пользователя и переименовывать свой чат. Это заменяет прежний запрет назначения агентом и требование ручного назначения человеком.

## Один исполнитель и актуальный статус

- Todo: открытая задача без исполнителя.
- In progress: открытая задача с одним назначенным человеком.
- Done: закрытая задача с выполненными критериями и результатом в main.

Метки синхронизирует .github/workflows/issue-status.yml при создании, назначении/снятии, закрытии/переоткрытии. Для старта агент использует .github/workflows/issue-claim.yml через `scripts/claim_issue.py`; workflow назначает ровно одного человека и сразу выставляет In progress. Закрытие означает готовность, а не отмену задачи. Несколько исполнителей — конфликт, работу не начинать.

## Автоматическое назначение без гонки

Простая последовательность «прочитать свободное issue → назначить себя» допускает гонку: два агента могут прочитать одно состояние. Оба workflow используют одну группу `issue-coordination-НОМЕР`, `cancel-in-progress: false` и `queue: max`. GitHub выполняет один запрос этой группы за раз; остальные ждут. [Официальные правила concurrency](https://docs.github.com/en/actions/reference/workflow-syntax-for-github-actions#concurrency).

1. Агент получает свой аккаунт через `gh api user --jq .login`, а не из git author или чужого issue. У коллег должны быть отдельные GitHub-подключения; workflow назначает `github.actor`, произвольного исполнителя передать нельзя.
2. Проверяет выбранное issue, зависимости и готовность результатов в main. Занятое issue не берёт, даже если назначен тот же аккаунт: его мог занять другой чат этого человека. Продолжение ранее начатой работы допускается в том же чате по сохранённому успешному запросу; передача в другой чат требует явного поручения и проверки отсутствия параллельной работы.
3. Выполняет из корня `python3 scripts/claim_issue.py НОМЕР`. Скрипт создаёт уникальный request ID, отправляет workflow и ждёт именно свой запуск. В очереди workflow заново читает issue, сверяет штатные зависимости с реестром и их закрытие, затем назначает отправителя и In progress одной записью. Сторонние метки сохраняются.
4. Перед кодом скрипт проверяет успешность своего запуска, единственного исполнителя и live метку. Второй запрос увидит уже назначенное issue и получит отказ, включая запрос другого чата того же аккаунта. Агент не обходит отказ через `gh issue edit --add-assignee` или прямой PATCH.

Для проверки без назначения: `python3 scripts/claim_issue.py НОМЕР --dry-run`. Это не даёт права начать работу. Отказ, отмена, недоступный workflow или неизвестный результат — не начало задачи. При таймауте проверить предыдущий run по URL/request ID: он ещё может завершиться назначением; не отправлять новый запрос вслепую. Очередь допускает до 100 ожидающих запусков; отменённый запрос не является захватом.

Ручная переназначенная задача или снятие исполнителя обходят очередь и не являются автоматической передачей работы. Во время запуска/исполнения не менять владельца без согласованной передачи. Агент повторно проверяет назначение перед отправкой результата; при изменении останавливается и не снимает чужое назначение. Очередь защищает от одновременных агентских запросов, а не от сознательного ручного обхода правил.

Перед стартом разработчик/агент читает live issue и проверяет:
1. Есть успешный результат собственного запроса назначения; поручение соответствует аккаунту отправителя и единственному исполнителю, статус действительно In progress.
2. Коллега не ведёт ту же задачу. Назначение другому человеку — запрет старта; общий аккаунт/исполнитель не заменяет проверку чата/ветви, если одна задача уже выполняется.
3. Все прямые зависимости выполнены, закрыты, их результат в main, проверки пройдены. Закрытая без реализации или ветка без merge не снимает блокировку.
4. Рабочее дерево чистое либо чужая работа изолирована; отдельная ветвь codex/v1-xx-короткое-имя и отдельный рабочий каталог при параллельной работе.

Назначение не обходит зависимости. Workflow проверяет закрытие предшественников, агент дополнительно проверяет их результат в main и проверки. Если задачу вручную назначили до готовности, не писать зависимый код; сообщить блокер. Все новые задачи первоначально Todo, без назначений.

## Порядок и предотвращение коллизий

После V1-03 можно разделить V1-04 и V1-05. После V1-09 — V1-10 и V1-11. После V1-13 — развёртывание V1-17, затем проверку реальной PWA на HTTPS в V1-16; сценарии можно готовить заранее. Точные зависимости — в issue и штатном Blocked by.

До параллельного изменения общей миграции, API-клиента, auth, маршрутов, токенов или Compose согласовать, кто меняет файл. Не брать незавершённые изменения коллеги в свой коммит. Миграциям давать уникальные имена/порядок, после merge обновить main и проверить совместный запуск. Не нужен дополнительный сервис блокировок.

Для занятой задачи фиксировать ветвь и краткий состав текущей работы в issue; при длительной паузе договориться о передаче, а не молча снимать/переназначать владельца. Изменение исполнителя во время работы — остановить изменения и согласовать передачу. Статус и поручение проверять повторно перед отправкой результата.

## Одна задача — один чат

Подтверждено заказчиком 12.10.2026 в чате анализа репозитория: каждый issue реализуется в новом чате, чтобы ограничивать объём контекста. Чаты создаёт пользователь; агент рекомендует следующую задачу и её название. Приоритет первого пользовательского результата — ручной учёт спортсменов, контактов и состава групп; технические зависимости сохраняются.

- Название чата: `V1-xx · #номер — краткий результат`, например `V1-02 · #150 — Вход сотрудников и права доступа`. Агент сам вызывает `set_thread_title` для своего чата. В копируемом промпте первой строкой писать «Переименуй этот чат в …», а не выдавать название только отдельно. Если инструмент недоступен, явно сообщить об этом и не утверждать, что чат переименован.
- Новый чат начинает с актуального main, AGENTS.md, краткой памяти, этих правил и полного live issue. Старый диалог не заменяет документы и проверку исполнителя/зависимостей.
- Существенные решения и ограничения сохранять в относящихся документах и краткой памяти, результаты проверок — в отчёте задачи с коммитом/PR. Не переносить полную переписку и не дублировать статусы GitHub отдельной очередью.
- В финальном отчёте указывать следующую рекомендуемую задачу: ID, ссылку, причину выбора, готовность прямых зависимостей и один копируемый промпт с точным названием/переименованием, автоматическим назначением, ссылкой на issue и `docs/task-agent-prompt.md`. Повторно проверить live статусы: не рекомендовать занятую коллегой задачу как свободную. Если готовых задач нет, назвать блокер. Рекомендация сама не резервирует следующий issue: назначение выполняет агент нового чата после поручения пользователя.

После фактического завершения V1-01 в main следующая задача — V1-02 / #150. Далее выбирать по графу зависимостей и приоритету реестра/групп, а не по устаревшему состоянию предыдущего чата.

## Завершение

Выполнить критерии issue и необходимые проверки, обновить относящиеся документы, создать коммит и push только файлов задачи; проверить успешность. Доставить результат в main установленным способом. PR можно использовать для удобства, но In review и ревью коллеги **не обязательны**. Автор может завершить PR после проверок в пределах предоставленного ему разрешения; этот документ сам по себе не даёт разрешения обходить защиты репозитория.

Закрывать issue после появления результата в main и выполнения критериев, указав коммит/PR и результаты проверок. Workflow поставит Done. Ветки/статус не заменяют выполненные проверки. При блокере или незавершённой приёмке не закрывать задачу.

Один назначенный issue — одна текущая работа; новую задачу пользователь поручает в новом чате, агент автоматически выполняет безопасное назначение. [Промпт исполнителя](task-agent-prompt.md).
