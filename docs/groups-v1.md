# Группы и история состава V1-06

12.10.2026, [#154](https://github.com/NikishGum/JudeOSLite/issues/154). Владелец/администратор в выбранном филиале создаёт, переименовывает и архивирует группы, выбирает карточки из ручного реестра, включает/исключает/переводит с датой действия. В карточке участника видна вся история; при создании можно сразу выбрать группу и дату включения.

## Схема и календарь

Миграция 0006 добавляет training_groups и group_memberships; 0001–0005 не меняются. Участник состава — **club_memberships.id**, никогда participantId. Составные FK (group_id,club_id) и (club_membership_id,club_id) запрещают чужой филиал. UNIQUE(id,club_id,group_id,club_membership_id) позволяет будущему снимку ссылаться на точный источник, группу и карточку; удаление используемых источников RESTRICT.

Периоды `[from,until)`: начало включено, конец исключён; null — без окончания. Строгие календарные YYYY-MM-DD от 0001; дата начала не раньше joined_on. Будущие даты разрешены. Дата исключения/перевода строго внутри периода, позже from и раньше until, если он задан. Операция не удаляет интервал и не меняет его начало/ключи. Исключение в первый день отвергается, чтобы не оставлять пустой период и не удалять исторический ID.

Инженерное решение v1: одна локальная карточка одновременно состоит максимум в одной группе. Проверка запрещает пересечения как внутри одной пары, так и между группами; гостевые/параллельные включения не создаются. Перевод одной транзакцией закрывает старый период на дату и добавляет новый с этой даты, сохраняя прежний until. Возврат в прежнюю группу — новый период, прежние ID сохраняются. Перенос joined_on за уже существующее начало группы запрещён.

Исторический состав вычисляется именно на выбранную дату: from ≤ date < until. Архивные группы/карточки остаются в истории с явной подписью; текущий флаг архива не скрывает старые периоды. Архив группы запрещает новые включения и переименование, сохраняет интервалы; исключить/перевести из архивной группы можно. Архивная карточка допускает исключение, но новое включение/перевод требует возврата карточки. Архив филиала запрещает все изменения, историческое чтение остаётся. Название/ФИО отображаются актуальные, интервалы датированы; их переименование не выдаётся за копию прежнего имени.

## API и права

`G = /api/clubs/{clubID}/groups`, `M = /api/clubs/{clubID}/participants/{membershipID}/groups`.

| Запрос | Контракт |
| --- | --- |
| GET G | state=active (по умолчанию)/archived/all; Group[] |
| POST G | {name,version:0}; 201 Group |
| PUT G/{groupID} | {name,version}; 200 Group |
| POST G/{groupID}/archive | {version}; 200 Group; повтор с актуальной версией безопасен |
| GET G/{groupID}/roster?date=YYYY-MM-DD | Interval[] на обязательную выбранную дату, включая архивные карточки |
| GET M | Interval[] всей истории карточки по from/id |
| POST M | {groupId,from,until?:null/дата}; 201 Interval |
| POST M/{intervalID}/exclude | {date,version}; 200 закрытый Interval |
| POST M/{intervalID}/transfer | {date,version,groupId}; 200 новый Interval; закрытие исходного и создание нового атомарны |
| POST /api/clubs/{clubID}/participants | Прежний контракт + initialGroup?:{groupId,from}; карточка, начальный интервал и оба аудита одной транзакцией |

Group: id,clubId,name,archived,version. Interval: id,clubId,groupId,membershipId,groupName,fullName,birthDate,cardArchived,groupArchived,from,until,version. Контактов в составе/истории нет. initialGroup разрешён только при POST новой карточки; в PUT отвергается.

Все endpoints auth.Require и RequireClub(administrator): владелец — сеть, администратор — свои филиалы. Trainer не получает весь состав/реестр только по роли в club. Доступ к назначенным группам появится через фактические правила/занятия V1-07–V1-09; отдельной group_trainers или системы назначений нет. Чужие/несуществующие/неверные ID — одинаковый 404. Origin/CSRF обязательны, ответы no-store.

400 invalid_input; 409 version_conflict/interval_overlap/group_archived/club_archived; 404 not_found; безопасный 503 not_ready. Название trim, 1–200 символов без управляющих; неизвестные поля/неполные даты/неверные версии отвергаются. Названия не уникальны и не заменяют ID.

## Блокировки, аудит и следующие задачи

Запись: actor FOR SHARE → живая session FOR SHARE → локальная administrator-роль FOR SHARE → clubs.RequireActive → participant FOR UPDATE → club_membership FOR UPDATE → целевая группа FOR SHARE → интервал. Все операции одного состава сериализуются на карточке; версии интервала/группы предотвращают тихую перезапись. Начальное включение держит блокировки новых participant/card и группы в транзакции реестра. `auth.LockClubAdministrator` используется также записью реестра, проверяя session ещё раз после HTTP middleware.

DB-trigger guard_group_interval использует тот же parent lock и отвергает пересечения даже при прямой SQL-записи; дополнительного расширения PostgreSQL нет. Ключи/начало интервала неизменяемы. Для будущего открытия состава V1-09 придерживаться совместимого порядка блокировок и один раз фиксировать snapshot в транзакции занятия. `groups.ReadGroup(ctx,tx,club,id,true)` держит FOR SHARE и требует действующую группу; V1-07/V1-08 вызывают его после прав actor и clubs.RequireActive вместе с auth.RequireTrainer. Исторические чтения используют active=false.

Групповые операции не изменяют чужие предметные таблицы/снимки. training_sessions/attendance_records ещё не добавлены: V1-09 создаёт снимок, дальнейшие чтения открытого/закрытого журнала используют его, а не повторный расчёт состава. Тестовый consumer с составным FK демонстрирует сохранение источников open/closed после перевода/архива, без production-заготовок занятий.

Audit атомарен: actor,club scope,entity ID, action, версии/архив группы; для состава membershipId/groupId/from/until/version. Без ФИО, даты рождения, контактов и секретов. При отказе аудита откатывается вся карточка/начальный состав или обе половины перевода.

Формы сохраняют ввод при ошибках, блокируют двойной submit. При конфликте есть явная загрузка актуальных данных со сбросом формы. Ключи соседних предметных компонентов различаются по типу и филиалу: проверка смены филиала выявила и устранила сохранение старых DOM-блоков при одинаковых React keys. Чтения отменяются, результаты мутаций после размонтирования не возвращают данные прежнего сотрудника/филиала. Поиск реестра с пагинацией 50 позволяет выбрать однофамильцев отдельно. Начальную дату включения вводят явно.
