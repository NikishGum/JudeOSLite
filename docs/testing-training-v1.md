# Расписание, история и конкурентные отметки V1-15

12.10.2026, [#163](https://github.com/NikishGum/JudeOSLite/issues/163).
Исполняемые проверки — `backend/tests/integration/training`. Результат QA — реальные
HTTP handlers с живыми сессиями/CSRF, PostgreSQL и миграциями 0001–0010. Production
handlers и миграции не менялись: в покрытых сценариях дефектов не обнаружено.

## Запуск

Нужны Go 1.27.2, PostgreSQL 18.6 и отдельная тестовая БД с правом CREATE DATABASE.
**Только disposable PostgreSQL:** каждый верхнеуровневый тест создаёт отдельную
`judeos_training_*` БД, применяет настоящие миграции и удаляет её через cleanup.
Фикстуры содержат только синтетические имена/контакты/пароль; тестовый пароль
не предназначен для реального развёртывания. SQL задаёт исторические входные
данные и точки отказа; открытия/отметки/закрытия/коррекции/переводы/смены версии
вызываются через API. Архив карточки/филиала задаётся в SQL-фикстуре.

Из корня проекта:

```sh
docker run -d --name training163-db \
  -e POSTGRES_USER=test -e POSTGRES_PASSWORD=test-only -e POSTGRES_DB=test \
  -p 127.0.0.1:5432:5432 postgres:18.6-bookworm
docker exec training163-db pg_isready -U test -d test
```

Дождаться готовности сервера для TCP-подключений (первичный init PostgreSQL
может временно принимать только локальные подключения), затем из `backend/`:

```sh
export TEST_DATABASE_URL='postgres://test:test-only@127.0.0.1:5432/test?sslmode=disable'
go test -race -v ./tests/integration/training
go vet ./...
go test -race ./...
go build ./cmd/server ./cmd/migrate ./cmd/create-owner
```

После проверки: `docker rm -f -v training163-db`. Без `TEST_DATABASE_URL` интеграционные
тесты пропускаются; такой запуск не подтверждает критерии. Существующий
`.github/workflows/build.yml` задаёт URL PostgreSQL service и выполняет
`go test -race ./...`, поэтому новый пакет автоматически входит в CI.

Гонки используют общий стартовый барьер и независимые PostgreSQL-транзакции.
Сериализуемые команды сверяются с итоговыми строками и аудитом, а не только
HTTP-кодом. Отмена не создаёт отсутствия; закрытие заполняет все NULL как
absent/unknown/close_default ровно один раз. Повтор close/open после закрытия
сохраняет полный fingerprint. После замены прежний тренер получает 404;
старые marked_by/marked_at остаются.

Один из двух допустимых порядков конкурирующих команд может выиграть; тест
проверяет состояние именно его результата. Это ограниченные проверки гонок,
не доказательство всех возможных interleavings и не нагрузочное испытание.
HTTP/SQL имеют 20-секундный предел, чтобы зависший lock завершал тест ошибкой.

## Независимый контроль отчёта

Период 2000-02-01–2000-02-29 включительно. A: два closed с тремя участниками,
один empty closed, один planned и один open с отметкой. B: один closed с двумя
участниками и отдельная группа без занятий. Cancelled с illness и NULL,
retired planned и closed до/после периода исключаются из приведённых сумм.

| Набор | Closed | Planned | Open | Present | Absent | Unknown | Illness | Excused | Процент |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| A, включая empty closed | 3 | 1 | 1 | 2 | 4 | 1 | 2 | 1 | 33⅓% |
| B | 1 | 0 | 0 | 2 | 0 | 0 | 0 | 0 | 100% |
| Сеть | 4 | 1 | 1 | 4 | 4 | 1 | 2 | 1 | 50% |
| Сеть после illness → present в A | 4 | 1 | 1 | 5 | 3 | 1 | 1 | 1 | 62,5% |
| Только empty closed | 1 | 0 | 0 | 0 | 0 | 0 | 0 | 0 | null |

Ledger перечисляет сеансы/исходные marks независимо от SQL приложения;
он не читает текущие totals, состав или audit. Контрольные сетевые значения
дополнительно заданы вручную. Все сравнения выполняются по UUID, не названию.
Процент сети взвешен по отметкам, а не усреднён между филиалами. История correction
сохраняет прежнюю illness, текущие суммы используют present. При конкурентной
коррекции каждый ответ целиком совпадает с одним из двух ledger-состояний:
сеть, филиалы и группы никогда не смешивают разные состояния.

## Результаты и ограничения

На Cloud проверены все десять верхнеуровневых тестов с `-race` на настоящей
PostgreSQL 18.6, полный прежний backend suite/миграции, gofmt/vet/build и
frontend TypeScript/Vite production build. Итоговые SHA, CI и доставка в main
фиксируются в live issue/PR после успешной проверки финального коммита.

Это backend QA. Здесь не проверялись физические устройства, реальная установка
PWA, пользовательская приёмка, VPS/offsite restore; они остаются #164/#165/#166.
Новые платёжные, медицинские, Excel-тесты и требования большой нагрузки не добавлены.
