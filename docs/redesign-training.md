## Рабочий экран

«Занятия» объединяет дневную/недельную ленту, произвольный включительный период,
правила расписания и переход к конкретному журналу. Начальный день — сегодня
в timezone выбранного филиала. Неделя — понедельник–воскресенье вокруг выбранной
даты; «Сегодня» возвращает текущий день либо текущую неделю. Ручной период —
не более 366 дней. При ручном изменении границ включается «Период».
Время и фактическая дата строки берутся из сохранённой timezone занятия,
отличающаяся зона и окончание на следующие сутки подписаны явно.

Группа выбирается по UUID из разрешённого сервером списка, архивные группы
сохраняются. Недоступный ID из ссылки не заменяется одноимённой группой.
«Все группы · сбросить фильтр» явно снимает ограничение. Филиал выбирается
существующей оболочкой; смена филиала пересоздаёт feature-область.

Строки сгруппированы по реальным датам, имеют время, группу, тренера, текстовый
статус planned/open/closed/cancelled, разовое происхождение и ручное исключение.
Отмена остаётся в списке с причиной, перенос показывает исходную дату.
«Изменить занятие» раскрывает доступные перенос/замену/отмену. Ограничения
версий, дат и снимка остаются серверными. Четыре режима, предпросмотр, версии,
история исключений и дальние выбранные даты сохраняют API v1.

Журнал открывается по ID. Planned требует отдельного подтверждения, до него
снимок не создаётся. Будущий журнал доступен для чтения, открыть его можно
с локального дня занятия. Для тренера — последовательные карточки, кнопки,
три причины с отменой/Escape, возврат к предыдущему участнику и сводка.
На ПК состав расположен справа; на телефоне основное действие располагается
в одной колонке и текущая карточка получает фокус/прокрутку. Переход только
после ответа сервера; двойное нажатие блокирует существующий pending guard.
Закрытие показывает точное число будущих absent/unknown, сохраняет атомарность
и идемпотентность API. Closed/cancelled у тренера доступны только для чтения.

Администратор/владелец читает снимок и исправляет одну closed-запись с отдельной
обязательной changeReason. История старого/нового значения, ожидаемая версия,
409 с перечитыванием, архив и отсутствие ограничения давности сохранены.
Многоролевой сотрудник получает действие отметок только для своего фактического
занятия и живой trainer-роли; журнал администратора остаётся отдельным действием.
Сервер повторно проверяет каждый доступ. Контракты и транзакции:
[attendance-v1](attendance-v1.md), [corrections-v1](corrections-v1.md).

## Минимальный контракт для RD-02/RD-05

`frontend/src/features/sessions/navigation.ts` экспортирует `sessionHref(clubId, options)`.

| Параметр URL | Значение |
| --- | --- |
| `/clubs/:clubId/sessions` | Доступный филиал и раздел занятий |
| `group` | Необязательный UUID группы, явный фильтр |
| `session` | Необязательный UUID конкретного занятия, открывает его журнал |
| `from`, `through` | Включительные даты `YYYY-MM-DD`; для восстановления списка |
| `view` | `day`, `week`, `period` |
| `journal` | `trainer` для фактических отметок; `admin` для чтения/коррекции |

Пример использования из главной:

```ts
sessionHref(club.id, {
  groupId: session.groupId,
  sessionId: session.id,
  from: session.date,
  through: session.date,
  view: 'day',
  journal: 'trainer',
});
```

Параметр `journal` не даёт прав: trainer-only всегда использует trainer endpoint,
manager с `trainer` также проходит серверную проверку роли и actual trainer ID.
При наличии group проверяется принадлежность загруженного session.
Неизвестные/чужие записи не заменяются первой доступной записью.

Использовать обычный `<a href={sessionHref(...)}>`, без перехвата в старый
`routePath`, который пока не хранит параметры session/date. Такие переходы
создают обычную history entry, проходят существующий beforeunload guard,
перезагружают авторизованный серверный контекст; direct/reload/back/forward
проверены. Редактирование фильтров заменяет текущую запись history, сохраняя
`prideIndex`; в URL нет имён, отметок, причин, черновиков и токенов.

[Согласованный RD-02 контракт](https://github.com/NikishGum/JudeOSLite/issues/185#issuecomment-6166323309)
использует тот же `?group=`. Переход из detail группы монтирует календарь с этим
ID. RD-02 c868fc9 вошла в main через PR #191/eabae80 и объединена с RD-03;
новый browser-сценарий проверяет сам переход из detail группы. RD-03 не меняет
занятые RD-02 `app/App.tsx`/`app/navigation.ts`, shared/API/lifecycle/PWA или
токены. Совместный результат проходит CI обоих браузеров.

`trainingChanged()` отправляет существующее DOM-событие `attendance-changed`
без payload после **подтверждённого сервером** open/mark/close/correct, изменения
занятия и сохранения правила. Read-only главная/отчёт могут подписаться и
перечитать разрешённые API; подписку нужно снять при unmount, запросы отменять
при смене пользователя/назначений/филиала. Существующий OwnerDashboard уже
слушает это событие. Новая вкладка или повторный вход всегда читает сервер;
событие не является хранилищем или межвкладочной очередью. Офлайн-очереди нет.

## Визуальные границы

Operate в существующей [Working Panel](../design-system/prototypes/dashboard/DESIGN.md):
Rubik, оригинальный PRIDE, плоские строки с разделителями, текстовые статусы,
зелёное присутствие, янтарное отсутствие/открытый журнал. На ПК карточка
участника и состав рядом, на телефоне последовательная работа. Кнопки отметок
56px; на телефоне поля и основные действия 16px; native Dialog причин/закрытия с фокусом,
Escape и safe-area. Глобальный DESIGN.md и исходные токены не изменены.
