# Вход сотрудников и доступ V1-02

12.10.2026, [#150](https://github.com/NikishGum/JudeOSLite/issues/150). Go/React/PostgreSQL; публичной регистрации нет. Управление филиалами/администраторами — V1-03, тренерами — V1-04. Полная предметная матрица — V1-14.

## Первый владелец

Сначала применить миграции. Из работающего локального Compose:

```sh
docker compose --env-file deploy/.env -f deploy/compose.yml exec app \
  /app/create-owner --login owner --name 'Владелец сети'
```

При разработке на хосте, из backend с DATABASE_URL/PGPASSWORD:

```sh
go run ./cmd/create-owner --login owner --name 'Владелец сети'
```

Команда требует терминал, дважды читает пароль без отображения; пароль не передаётся флагом, переменной окружения или файлом. 12–128 байт, пробелы пароля сохраняются. Логин нормализуется trim/lower: 1–100 ASCII букв/цифр и `._@+-`, начинается буквой/цифрой. Имя — 1–200 символов. Две команды сериализуются транзакционной блокировкой: только одна создаёт первого владельца; при наличии любого owner повтор запрещён, в том числе отключённого. Команда не меняет существующий пароль и не служит восстановлением аккаунта.

## Origin и cookie

Для HTTP только на локальном компьютере: `APP_ORIGIN=http://localhost:8080`, `AUTH_INSECURE_LOCAL=true`. Пример deploy/.env.example задаёт эти значения. Для Vite: origin `http://localhost:5173`; Go слушает :8080, API проксируется Vite. Origin должен совпадать с адресом в браузере, включая схему и порт; localhost и 127.0.0.1 различаются.

Для HTTPS: `APP_ORIGIN=https://crm.example.org`, `AUTH_INSECURE_LOCAL=false` (по умолчанию). Без явного origin сервер использует безопасный `https://localhost`; рабочий адрес надо настроить. Origin без пути, slash, userinfo, query или fragment. Небезопасный режим разрешён только для HTTP loopback origin, а не публичного домена. На VPS остаётся HTTPS-прокси из V1-17, БД не публикуется.

Cookie `__Host-pride_session` и `__Host-pride_csrf`: Secure, HttpOnly, SameSite=Strict, Path=/, без Domain, срок 12 часов. Локальный HTTP-режим использует отдельные имена `pride_session_local` / `pride_csrf_local` без Secure. Случайные значения по 32 байта, в БД только SHA-256. В JSON нет сессионного токена или парольного хеша; me возвращает отдельный CSRF-токен, необходимый клиенту для изменений. Клиент держит его только в памяти; localStorage/sessionStorage не используются. API-ответы no-store, пароли, cookie и тела запросов не логируются.

Пароли — Argon2id, соль 16 байт, ключ 32 байта, 64 MiB, три прохода, один поток. Профиль закодирован в хеше и строго проверяется; произвольные параметры из повреждённого хеша не выделяют память. Поддерживаемые библиотеки закреплены по официальным источникам: [x/crypto v0.58.0 / argon2](https://pkg.go.dev/golang.org/x/crypto@v0.58.0/argon2), [x/term v0.47.0](https://pkg.go.dev/golang.org/x/term@v0.47.0). Не более двух параллельных вычислений при HTTP-входе.

## API

| Запрос | Контракт |
| --- | --- |
| POST /api/auth/login | JSON login/password, обязательный Origin приложения; 200 status=ok и новые cookie. Неверный/неизвестный/отключённый аккаунт — одинаковый 401 invalid_credentials. Вход отзывает предыдущую сессию из cookie |
| GET /api/auth/me | 200: user {id, login, displayName, isOwner}, clubs [{id, name, timezone, archived, roles}], csrfToken. Нет действующей сессии — 401 unauthorized |
| GET /api/auth/clubs/{id} | Только доступный филиал; чужой/несуществующий/неверный ID — одинаковый 404. Возвращает метаданные и текущие роли, без чужих назначений |
| POST /api/auth/logout | Origin и X-CSRF-Token; отзыв текущей сессии и удаление cookie после успешной записи в БД |

Любая защищённая операция изменения проходит `auth.Service.Require`: живые сессия/аккаунт и CSRF-хеш, Origin и X-CSRF-Token. Login защищён от login CSRF точным Origin ещё до обработки пароля. Некорректный CSRF — 403 csrf_failed; недоступная БД — безопасный 503, без SQL/DSN. При 401 клиент удаляет данные предыдущего сотрудника и переводит на вход. При сетевой ошибке выхода UI не сообщает об успешном выходе и позволяет повторить. Двойное нажатие блокируется до результата.

Ограничение входа: 5 попыток на нормализованный login и 20 на IP за 15 минут, включая успешные; 429 и Retry-After. Ограничитель в памяти одного Go-процесса, максимум 10 000 ключей, истёкшие удаляются. Перезапуск обнуляет окна. IP берётся только из RemoteAddr; X-Forwarded-For не доверяется, поэтому за HTTPS-прокси клиенты могут делить IP-квоту. Это сознательная простая граница одного сервиса; настройка доверенных прокси не реализована. Возвращается одинаковая ошибка для неизвестного логина с холостым вычислением хеша.

## Серверные права и схема

0002_staff_access.sql создаёт staff_users, staff_club_roles, staff_sessions и минимальный clubs для FK/доступного списка. Поля clubs уже соответствуют схеме V1-03; там следует добавлять управление, а не создавать таблицу повторно. Owner — глобальный флаг, administrator/trainer — назначения в конкретных clubs, несколько ролей/клубов разрешены.

`Require` оборачивает каждый предметный handler; `CurrentUser(ctx)` применяется только внутри него. `RequireClub(ctx, userID, clubID, roles...)` повторно читает текущие роли и disabled_at; роли задаёт серверный handler, не форма. Владелец получает любой филиал, остальные — только назначение с запрошенной ролью. Список me исключает архивные филиалы; чтение доступных архивных метаданных разрешено для будущей истории. Предметные операции отдельно запрещают новые изменения в архивном филиале.

При изменении disabled_at с NULL на значение DB-trigger отзывает все сессии. Вход блокирует строку пользователя перед созданием сессии, исключая гонку с отключением. Повторное включение не оживляет старые сессии. Удаление роли действует на следующий запрос без повторного входа; исторические FK сохраняются. Истёкшие сессии удаляются при успешном входе.

Назначение trainer даёт только обнаружение своего филиала. Эта проверка не разрешает тренеру произвольные группы или занятия: предметные handlers будущих задач обязаны проверять фактического назначенного тренера. Нет универсального permission engine.

UI проверяет сессию до показа рабочего пространства, подтверждает выбранный филиал через API, повторяет проверку при возврате в окно и каждые 30 секунд в видимой вкладке. Прямой путь /clubs/{id} не даёт доступ без сессии. Серверные ограничения действуют немедленно; периодическое обновление UI лишь убирает устаревший экран.

## Проверки

```sh
cd frontend && npm ci && npm run build
cd ../backend
go vet ./...
TEST_DATABASE_URL='postgres://test:test-only@127.0.0.1:5432/test?sslmode=disable' go test -race ./...
go build ./cmd/server ./cmd/migrate ./cmd/create-owner
```

TEST_DATABASE_URL — только тестовая БД с CREATE DATABASE. Тесты создают и удаляют собственную БД; без переменной явно пропускаются. CI запускает их на PostgreSQL 18.6. auth_test.go проверяет конкурентный bootstrap, пароли, cookie/хеши, вход, выход, ротацию/expiry/revoke/disable, CSRF, owner/admin/trainer и несколько назначений, немедленный отзыв роли, одинаковый отказ для чужого ID и throttling. Миграционные тесты проверяют обе миграции и checksum.

Локально выполнены Go vet/build/race с реальной PostgreSQL, frontend build, production Docker build и Compose clean/rerun/restart/readiness recovery. Govulncheck: 0 уязвимостей в используемых пакетах/вызовах; модульный advisory GO-2026-5932 относится к неиспользуемому openpgp, auth использует argon2. Chromium 151 на 320/390/1280 px: без горизонтальной прокрутки/JS-ошибок; защищённый прямой путь, неверный пароль, owner с двумя филиалами, выбор/перезагрузка, выход и повтор после сетевой ошибки, двойное нажатие, изоляция admin, отказ CSRF, отзыв роли и очистка UI после disable прошли. Bootstrap реально выполнен через скрытый терминальный ввод на синтетической БД. Итоговый CI записывается в отчёте issue. HTTPS/VPS, реальные iPhone/Android и пользовательская приёмка не входят в эту проверку.
