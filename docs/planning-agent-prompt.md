# Промпт агента: подробный план разработки JudeOSLite v1

Назначение: передать этот документ агенту в корне репозитория JudeOSLite. Результат агента — **план в Markdown, не реализация приложения**. Архитектура и БД уже подготовлены для обсуждения; нельзя молча считать все предложения утверждёнными бизнес-правилами.

---

Ты работаешь над JudeOSLite — внутренней CRM сети дзюдо-клубов PRIDE. Подготовь качественный поэтапный и пораздельный план разработки первой версии на основе документов репозитория. План должен состоять из небольших работ с одним проверяемым результатом. Заказчик прямо запретил сейчас реализовывать приложение: создавай/обновляй только документацию планирования.

## 2. Что должно получиться

Создай `docs/development-plan-v1.md` — один основной документ с удобным оглавлением, этапами, разделами и карточками небольших задач. Для него обнови указатель базы знаний и краткую память, сохрани происхождение новых решений. В корне не создавай длинный дубликат плана.

Перед карточками задач дай:

1. Статус: это план, реализация не начата; какая версия архитектуры/схемы использована.
2. Карту этапов с результатом каждого, зависимостями и критериями перехода.
3. Список B01–B10, конкретные вопросы заказчику и какие задачи зависят от ответа.
4. Список архитектурных расхождений, если обнаружены. Не исправляй их молча и не маскируй как уже согласованные условия.
5. Краткую карту контекста с действительными ссылками для будущего исполнителя.

После карточек дай матрицу покрытия требований R01–R12, таблиц T01–T26, предложений P01–P08 и значимых рисков; затем порядок первых доступных задач, контрольные точки приёмки и остаточные неизвестные условия.

План не должен содержать фиктивную «готовую интеграцию», код приложения, SQL-миграции к выполнению, credentials, выдуманные endpoints/подпись iPay или бизнес-ответы, которых заказчик не дал. Можно указать предполагаемые файлы будущей реализации как область задачи, явно отличая их от существующего контекста.

## 3. Требования к дроблению

Одна задача = один самостоятельный проверяемый результат и одна основная область работы. Примеры допустимого размера: контракт одного endpoint, ограничение пары связанных таблиц, одна транзакционная операция, одна форма, один важный интеграционный сценарий. Задачи «сделать backend», «реализовать CRUD участников», «подключить iPay», «создать всю БД», «сделать адаптивность» недопустимы.

- Если в пункте есть несколько независимо проверяемых действий, разбей его. Например: контракт формы → серверная операция → HTTP-обработчик → UI формы → проверка сквозного сценария, когда у каждого есть самостоятельный результат.
- Локальные проверки результата входят в задачу. Отдельная проверочная задача нужна для самостоятельного риска, интеграционного/сквозного сценария, а не для каждого тривиального поля.
- Обычно задача затрагивает один слой и 1–3 тесно связанных файла. Это ориентир: не дроби механически по файлам и не создавай пустые пункты «создать папку».
- Отмечай размер XS/S. Если задача требует нескольких законченных функций или получается M/L, раздели её до публикации плана. Не обещай выдуманное количество часов.
- Для CRUD разделяй список/поиск, создание, изменение, архивирование; отдельно права/контракты, если это независимая работа. Поведение с ошибкой/пустыми данными/на телефоне входит в критерии конкретного UI-результата.
- Для денег разделяй интервалы цены, генерацию начисления, корректировку, расчёт остатка, подтверждение платежа, зачёт, отмену зачёта и сторно.
- Для iPay разделяй транспорт, кодировку, доверие/подпись, каждое сообщение, повтор, конфликт, неизвестный результат, ACK и сверку. Рабочую подпись не проектируй по заголовку из старого PDF без спецификации.
- Для расписания разделяй правило, изменение с даты, генерацию, повтор генерации, ручные исключения, открытие со снимком состава, отметку и прошлую правку.
- Для импорта разделяй чтение согласованного формата, нормализацию, ошибки, сопоставление, предпросмотр, подтверждение и повтор применения.

Ориентир — примерно 80–120 содержательных небольших задач для всего описанного объёма. Число не критерий качества: не дополняй пустыми пунктами и не объединяй самостоятельные результаты ради лимита. Полностью покрой согласованный объём.

## 4. Карточка каждой задачи

Используй этот формат с заполненными значениями, без TODO и общих заглушек:

```text
### <стабильный ID>. <действие и конкретный результат>
Раздел/этап: <модуль и этап>
Тип и размер: <документ / БД / backend / API / UI / проверка / эксплуатация>; XS или S
Основание: <Rxx/Pxx/Txx и связанные Bxx>
Результат: <одно предложение о готовом результате>
Границы: <что входит и какой соседний результат относится к другой задаче>
Зависимости: <существующие ID предшествующих задач, не только название этапа>
Неизвестные условия: <конкретный Bxx, влияние и независимая часть; либо нет>
Контекст: <2–4 точные Markdown-ссылки на существующие документы/разделы>
Область изменений: <предполагаемые будущие файлы/таблицы; не выдавать за существующие>
Критерии готовности: <2–5 наблюдаемых условий, включая релевантные ошибки/права>
Проверка: <конкретный сценарий и ожидаемый результат, соразмерный риску>
Передача дальше: <какой контракт/артефакт потребляет следующая задача>
```

ID стабильны: например AUTH-01, MEM-04, TRAIN-12, FEE-07, PAY-18, IMPORT-05. Не повторяй ID и не меняй их при простой перестановке. Зависимости должны образовывать ациклический граф; задача не ссылается на себя/несуществующий ID.

## 5. Примеры нужной глубины

### Пример A: FEE-07. Транзакция изменения цены с выбранного месяца

Тип: backend, S. Результат: одна сервисная операция закрывает старый fee_term и создаёт новый без пересечения. Зависимости: контракт интервалов цены, миграция fee_terms, проверка права администратора на клуб. Контекст: [T14](database/schema-v1.md#t14), [транзакции](database/schema-v1.md#transactions), [месячные взносы](architecture-v1.md#billing). Область: сервис billing и его PostgreSQL-проверка.

Критерии: смена с ноября не меняет октябрь; повтор команды/параллельная правка не создают перекрытие; чужой клуб не изменяется; корректировка уже выставленного начисления не маскируется этой операцией. Проверка: начальная цена 10000 копеек до ноября, новая 11000 с ноября; два последовательных непересекающихся интервала и прежняя сумма октябрьского charge. UI выбора месяца и HTTP-контракт — другие задачи.

### Пример B: PAY-18. Проверить повтор успешного TransactionResult

Тип: интеграционная проверка, S. Результат: доказано отсутствие повторного денежного эффекта для одной принятой попытки. Зависимости: обработчик результата, сохранение событий, payments и согласованный зачёт B03. Контекст: [T19–T21](database/schema-v1.md#t19), [зачёт](database/schema-v1.md#t23), [платёжный поток](architecture-v1.md#ipay), [протокол](knowledge-base/ipay-protocol.md).

Критерии: после повторной доставки один payments; сумма зачёта не удвоена; число доставок события увеличено; ответ соответствует договорному ACK; изменённые существенные параметры идут в отдельный разбор. Проверка: синтетическая цепочка с одинаковыми ID и повторным результатом в настоящей тестовой PostgreSQL. Это не задача «реализовать весь iPay» и не замена договорного тестового стенда.

## 7. Обязательное покрытие рисков

В задачах/матрице покажи конкретное место проверки:

- Wrong-club ссылки и запросы; отсутствие финансов у тренера, включая прямой API/поиск/счётчики.
- Общая идентичность участника не открывает контакты/справки чужого клуба.
- История группы и снимок занятия после перевода; отменённое занятие не превращается в пропуски всех участников.
- Изменение расписания с даты не перезаписывает отмену/ручную замену и не создаёт второй слот.
- Цена с месяца, нулевой взнос, повтор генератора, прошлое начисление и корректировка после оплаты.
- Корректировка ниже зачтённой суммы возвращает превышение в нераспределённые деньги без потери платежа.
- Повтор TransactionStart возвращает прежний ServiceProvider_TrxId; UUID не отправляется в поле длиной 12 символов.
- Сумма TransactionResult берётся из начала; повтор/конфликт/неизвестное начало и неверная подпись не создают второй/выдуманный платёж.
- ACK после надёжного сохранения; TransactionResult не получает запрещённый XML Error.
- Сторно с обратными allocations; частичное сторно не объявляется поддержанным без B07.
- Сохранение ведущих нулей счёта; RequestId не используется как единственный ключ всей цепочки.
- Повтор импорта, неполная дата рождения, семейный телефон, неизвестное «б/о» и реальные источники старых остатков.
- Два параллельных платежа/корректировка, фиксированный порядок блокировок и проверка балансов в PostgreSQL.
- Все роли на телефоне/ПК; ошибка сети не отображается успешной отметкой; нет offline queue.
- Backup/restore и обработка накопившихся событий после недоступности по реальному договорному сценарию.

Для простых обратимых UI-правок не требуй бессмысленных зеркальных unit-тестов. Для целостности, денег и прав нужны проверяемые сценарии с ожидаемыми результатами; общая фраза «покрыть тестами» недостаточна.

## 8. Самопроверка и завершение

Перед публикацией плана проверь:

1. Все R/P/T покрыты ссылками на задачи; B отмечены у зависимых работ, нет молчаливых бизнес-догадок.
2. Каждый пункт имеет один результат, границы, предшественников, ссылки и критерии; нет M/L или крупного блока, спрятанного в подпункты.
3. ID уникальны, граф зависимостей без цикла, первые задачи реально доступны.
4. Контекстные ссылки существуют; конкретные источники рядом с задачей, а не только в начале документа.
5. Разделы БД/API/UI и операции согласованы между собой; запрет финансов тренеру действует на сервере.
6. Синтетические проверки и рабочее подключение iPay разделены; неизвестные из PDF/договора не придуманы.
7. Mobile-first встроен в задачи экранов; PWA-установка не означает реализацию офлайна.
8. Никакие файлы приложения, секреты и реальные персональные данные не созданы.

По AGENTS.md закоммить только план и относящиеся к нему обновления документации, отправь в репозиторий без force push и проверь успех. Если есть чужие незавершённые изменения, не включай их. В итоговом ответе дай ссылку на план, число этапов/задач, критические B и подтверждение commit/push. Не начинай реализацию после создания плана без отдельной команды заказчика.
