# iPay: разбор присланной структуры обмена

Дата разбора: 11.10.2026. Статус: сведения предоставленного документа; применимость к рабочему договору клуба не подтверждена. Реализация и обращения к платёжным системам не выполнялись.

## Источник и ограничения

Заказчик приложил `3403_03_iPay_агрегатор_Обмен_с_поставщиком_услуг 2.pdf`, 20 страниц, название «Агрегатор iPay. Структура сообщений для обмена с поставщиком услуг». SHA-256: `1f0e8a8967f063a2ac7433cde196dc2e4dbf7ce03204fc05432378186876be3e`.

На титуле указан УАРС.3403.03, в колонтитулах — УАРС.3403.04. Метаданные CreationDate/ModDate: 17.07.2017; это дата файла, а не доказанный срок действия редакции. Введение на странице 3 ограничивает описание поставщиками, выставляющими задолженность в виде суммы. Исходный PDF находится у заказчика; в Git сохранён разбор, без копирования полного текста или двоичного файла.

Изучены все 20 страниц, включая примеры 14–18 и схему на странице 20; существенные таблицы и схема проверены визуально. Протокол имеет расхождения и недостающие условия, перечисленные ниже. Внешние ссылки/названия продуктов в старом PDF не проверялись как действующие сервисы.

## Транспорт и общая часть

По разделам 1.1 и 1.3, страницы 4 и 6:

- Все запросы идут от iPay на сервер поставщика услуг (будущую CRM).
- HTTP либо HTTPS, метод POST; XML-сообщение передаётся в параметре с именем `XML`. Конкретный Content-Type и подписываемое представление не указаны; не предполагать сырой XML в теле или определённую форму без уточнения.
- HTTP 200 обозначает успешную доставку сообщения. Ответ — XML в теле HTTP-ответа; успешная доставка сама по себе не подтверждает успешный платёж.
- Кодировка сообщений windows-1251; десятичный разделитель — запятая; логические значения — `Y`/`N`; дата/время — `YYYYMMDDhhmmss`. Часовой пояс явно не задан.
- Подпись передаётся в заголовке `ServiceProvider-Signature` в форме «алгоритм: значение». Сам алгоритм, секрет, вычисляемые байты и проверка свежести не описаны. VPN упомянут как рекомендация при технической возможности, а не обязательное условие.

| Поле запроса | Ограничение и смысл по таблице 1.2 |
| --- | --- |
| ServiceProvider_Request | Корневой элемент |
| RequestType | Обязательное, до 20 символов |
| DateTime | Обязательное, дата/время сообщения |
| ServiceNo | Необязательное, до 9 цифр; номер услуги у поставщика |
| PersonalAccount | Обязательное, до 30 символов; уникальный идентификатор плательщика **в пределах услуги** |
| Currency | Обязательное, до 3 цифр; BYN — 933 |
| RequestId | Обязательное, до 8 цифр; сохраняется в цепочке ServiceInfo → TransactionStart → TransactionResult |
| Language | Необязательное, RU/EN, по умолчанию RU |

Ответ имеет корень `ServiceProvider_Response`. Общая ошибка — `Error` со строками `ErrorLine`; при ошибке соответствующая типу запроса часть ответа не заполняется. Для ответа на TransactionResult есть отдельное ограничение, см. ниже.

## Сообщения и доступные функции

| Сообщение | Значение | Основные поля и результат | Страницы |
| --- | --- | --- | --- |
| ServiceInfo | Получить задолженность и данные для оплаты | Запрос содержит Agent. Ответ: Amount/Debt, возможные Penalty, Name, Address, Info | 7–8, 14 |
| TransactionStart | Начать оплату и проверить параметры | Amount, TransactionId, Agent, AuthorizationType с возможным Ident; необязательные изменённые Name/Address. CRM возвращает ServiceProvider_TrxId и возможную информацию для чека | 9–10, 15 |
| TransactionResult | Сообщить итог оплаты | TransactionId, ServiceProvider_TrxId, необязательный ErrorText. ErrorText присутствует при неуспешном завершении | 11, 16–17 |
| StornStart | Начать сторнирование успешной операции | TransactionId, ServiceProvider_TrxId, Amount. Ответ — общая часть | 12, 17 |
| StornResult | Сообщить результат сторнирования | TransactionId, ServiceProvider_TrxId, Amount, Storned (Y/N). Ответ — общая часть | 13, 18 |

В ServiceInfo можно управлять возможностью изменить сумму: `Amount/@Editable` (по умолчанию запрет), а также `MinAmount`, `MaxAmount`, `AmountPrecision`. Debt обязателен, формат F12,2. Name/Address необязательны и имеют собственный Editable. InfoLine позволяет показать пояснение; общая отображаемая информация ограничена 2000 символами. Эти поля — возможности протокола, а не согласованные настройки клуба.

TransactionId — идентификатор транзакции iPay до 12 цифр. ServiceProvider_TrxId — идентификатор CRM до 12 символов. Сумма поступает в TransactionStart; в TransactionResult отдельного Amount нет. Поэтому результат нужно связывать с сохранённым началом транзакции, а не вычислять сумму по текущему тарифу.

На странице 11 прямо запрещён элемент Error в ответе на TransactionResult. Примеры страницы 17 показывают предупреждение об ошибке на стороне поставщика в InfoLine. Это условие ответа на уведомление, а не разрешение безусловно зачесть неизвестный платёж. Успешное и неуспешное завершение необходимо различать по ErrorText и сохранять согласованное состояние операции.

Сторнирование описано как входящая цепочка от iPay. API инициирования возврата из интерфейса CRM этим документом не подтверждён. Отмена попытки оплаты и сторнирование ранее успешной операции — разные события.

## Порядок оплаты по документу

Раздел 1.10, страницы 19–20:

1. Поставщик формирует уникальный номер оплаты (лицевой счёт). Его назначение может зависеть от услуги: участник, договор, заказ и т. п.
2. Клиент выбирает услугу в ЕРИП и вводит лицевой счёт.
3. iPay запрашивает ServiceInfo; CRM возвращает сумму и сведения для проверки клиентом.
4. После подтверждения клиентом iPay отправляет TransactionStart; CRM проверяет параметры и выдаёт свой идентификатор транзакции.
5. iPay выполняет платёж и уведомляет CRM через TransactionResult; для клиента формируется чек.
6. На схеме предусмотрена повторная доставка TransactionResult при ошибке обработки/транспорта «в течение XX часов». Конкретный срок и интервал не определены. Таймаут доставки TransactionStart обозначен как основание отмены платежа, но его длительность не указана.

Страница 19 также содержит пример перехода на операционный сайт iPay с параметрами услуги, лицевого счёта и возможной суммы; адрес предоставляется после регистрации услуги. Рабочий адрес клуба не указан. Для внутренней первой версии такой переход не требуется по подтверждённым требованиям.

**Вывод из описанного потока:** «выставить счёт» может означать создать начисление в CRM и отдавать его остаток при запросе ServiceInfo. Отдельной команды исходящего создания счёта в iPay в этом PDF нет. Это архитектурная интерпретация; её применение к действующей услуге клуба ещё согласовать.

## Предложения для архитектуры, не утверждённые бизнес-правила

- Сопоставлять участника по привязке услуги и PersonalAccount. Не использовать ФИО как единственный автоматический ключ. Если ServiceNo не передаётся, способ определения услуги/клуба согласовать в настройке подключения.
- Внутренний идентификатор участника и платёжный лицевой счёт хранить отдельно. Лицевой счёт — строка с сохранением ведущих нулей; PersonalAccount уникален только в рамках услуги по источнику.
- Сохранять состояние попытки оплаты после TransactionStart; погашать начисления только после подтверждённого успешного TransactionResult. HTTP 200 и начало транзакции не равны оплате.
- Повторная доставка одного результата не должна повторно увеличивать полученную сумму. Область уникальности ключей и реакцию на противоречивые повторы уточнить у провайдера.
- Для сторнирования сохранить историю, а финансовый эффект менять после подтверждённого StornResult, без физического удаления платежа.
- Подтверждать корректное уведомление после надёжного сохранения события; ошибки разнесения разбирать отдельно. Не выдумывать XML Error там, где источник его запрещает. Невалидные/неаутентифицированные запросы обрабатывать по согласованному транспортному контракту.
- Нужны сверка с реестром и способ восстановления пропущенных результатов. API получения истории/реестра в этом документе не описан.

## Что уточнить до интеграции

1. Какая редакция применима сейчас; почему на титуле .03, в колонтитулах .04. Наличие Version в примерах, но не в таблице общей части; требования к этому полю.
2. Ошибки ссылок на поля: в некоторых таблицах ServiceProviderTrxId вместо ServiceProvider_TrxId; ссылки на Amount в ответах, где Amount не определён. Подтвердить схемы по тестовым сообщениям, не копировать опечатки.
3. Алгоритм подписи, параметры доверия, канонизация/кодировка подписываемых байтов, порядок проверки подписи запросов и формирования подписи ответов. Секреты в Git не сохранять.
4. Content-Type и способ передачи XML; требования HTTPS/VPN; адреса тестового/рабочего окружения, регистрация callback-адреса CRM, сетевой доступ и таймауты.
5. Коды услуг каждого клуба, передача ServiceNo и соответствие текущего кода ЕРИП полю PersonalAccount. Можно ли перейти на постоянный лицевой счёт участника.
6. В каких границах уникальны RequestId/TransactionId, могут ли повторяться после периода, как обрабатываются повторы/противоречия и результат без ранее сохранённого TransactionStart.
7. Сроки и интервалы повторов, восстановление после недоступности, получение реестра для сверки и обработка старых платежей до запуска.
8. Ограничения оплаты: изменение суммы, частичная оплата, переплата, несколько периодов, сторнирования и работа при отсутствии долга. Это также бизнес-решения заказчика.
