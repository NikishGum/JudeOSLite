# Ручной реестр участников V1-05

12.10.2026, [#153](https://github.com/NikishGum/JudeOSLite/issues/153). После входа владелец или администратор выбирает филиал и открывает «Участники филиала»: ручное создание, поиск, карточка, редактирование, архив и возврат. Полная дата рождения вводится явно; значения по умолчанию и восстановление дня/месяца из года отсутствуют. Группы/начальный состав добавляет V1-06.

## Схема и права

0004 добавляет participants (ФИО/дата рождения/version) и club_memberships (локальный контакт, дата вступления, архив/version). Существующие clubs, сотрудники, сессии и audit_events сохраняются; 0001–0003 не меняются. Каждое ручное создание создаёт новую идентичность и карточку одной транзакцией. ФИО и телефон/email не уникальны; одинаковый семейный контакт и однофамильцы разрешены. UNIQUE(participant_id,club_id) предотвращает повторную локальную связь одной уже существующей идентичности. API сопоставления/присоединения/объединения нет.

Owner управляет реестром любого филиала, administrator — только назначенного. Trainer не читает весь реестр по одной роли в филиале: просмотр назначенного состава появится в тренировочных задачах. Все handlers проходят auth.Require и RequireClub с administrator; чужой/несуществующий/некорректный клуб или ID карточки дают одинаковый 404. Поиск, список и контакты ограничены club_id. Ответы no-store, Origin/CSRF обязательны для изменений. Отключение и отзыв роли действуют на следующий запрос; внутри записи повторно проверяются и блокируются действующий actor и administrator-назначение.

Администратор может менять общие ФИО/дату рождения только при единственной связи идентичности с его филиалом. Архивная связь другого филиала тоже считается. Даже администратор двух филиалов общую идентичность не меняет; это право владельца. Поле canEditIdentity управляет формой, сервер независимо проверяет то же правило под блокировкой. Чужие контакты/ID связей не выдаются. Локальную карточку можно менять без identity в запросе, в том числе у общей идентичности. Owner меняет общее имя/дату, сохраняя локальные контакты и версии других карточек.

Архив/возврат меняют только archived_at/version локальной карточки. ID, joined_on, идентичность и ссылки сохраняются; DELETE API нет. Для будущей истории предусмотрен UNIQUE(id,club_id), FK на participant/club — ON DELETE RESTRICT. Таблицы занятий/отметок здесь не создаются. Архив всего филиала допускает историческое API-чтение, но запрещает создание, редактирование, архив и возврат участников через clubs.RequireActive в транзакции; UI рабочего выбора исключает архивный филиал по контракту V1-03.

## Валидация

- ФИО обязательно, 1–200 символов после trim, контактное имя необязательно до 200; управляющие символы запрещены.
- Даты строго YYYY-MM-DD, настоящие календарные даты с годом от 0001. Рождение ≤ вступление ≤ сегодняшний день **в зоне филиала**. Ограничения возраста не вводятся. Изменение общей даты рождения владельцем также проверяет даты вступления остальных карточек, включая архивные.
- contactKind — phone/email, значение обязательно до 254 символов. Телефон: 7–15 ASCII-цифр, + только в начале; пробелы, скобки и дефисы разрешены. Email проверяется net/mail как один адрес без display name. Внешняя проверка доставки не выполняется.
- Неизвестные JSON-поля, частичная/выдуманная дата, пустой контакт и неверные версии отвергаются; в ответах нет SQL, DSN или чужого payload.

## API

Префикс `B = /api/clubs/{clubID}/participants`. ID в пути — **club_memberships.id**, participantId — общая идентичность; не путать их в V1-06.

| Запрос | Контракт |
| --- | --- |
| GET B | {items,hasMore}; q — буквальная подстрока ФИО/локального контакта/контактного имени, без SQL wildcard; state=active (по умолчанию)/archived/all; page с 0, по 50 записей, порядок lower(full_name),id |
| GET B/{id} | Card, включая архивную карточку своего доступного филиала |
| POST B | {identity:{fullName,birthDate,version:0},joinedOn,contactKind,contactValue,contactName?,version:0}; 201 с Card; всегда новая идентичность |
| PUT B/{id} | {joinedOn,contactKind,contactValue,contactName?,version,identity?:{fullName,birthDate,version}}; identity опускается для локальной правки, 200 с Card |
| POST B/{id}/archive | {version}; 200 с Card |
| POST B/{id}/restore | {version}; 200 с Card |

Card: id,participantId,clubId,fullName,birthDate,participantVersion,joinedOn,contactKind,contactValue,contactName,archived,version,canEditIdentity. Даты — календарные строки без преобразования часового пояса. Состояние контакта и version принадлежат membership; participantVersion меняется только при реальной правке общей идентичности. Любой identity в PUT требует актуальной participantVersion и права владельца/единственного филиала; пропуск identity сохраняет существующие общие данные.

400 invalid_input; 403 identity_owner_required; 404 not_found; 409 version_conflict/club_archived; безопасный 503 not_ready. Поле q ограничено 200 символами; page 0–100000. Возвращается не более 50 карточек, hasMore определяет следующую страницу.

## Конкуренция и аудит

Запись блокирует actor/роль, активный club FOR SHARE, затем participant FOR UPDATE, затем membership FOR UPDATE. После блокировок проверяются число связей и обе нужные версии. Ошибка откатывает идентичность, локальную карточку и аудит вместе. BEFORE INSERT/UPDATE ключей membership берёт тот же participant lock: новая связь не пересекает проверку единственного филиала. Следующие задачи должны соблюдать этот порядок при работе с реестром; групповые операции не должны менять participant_id/club_id существующей карточки.

audit_events переиспользуется: club_id,actor_id,entity_type=club_membership,entity_id=membership ID, action created/updated/archived/restored, версии, participantId, joinedOn, состояние архива и признаки identityChanged/contactChanged. Без ФИО, даты рождения, контактного имени/значения, паролей/токенов. Это история операции, не копия персонального реестра. Повтор archive/restore с актуальной версией и уже нужным состоянием безопасен; устаревшая версия даёт конфликт.

Форма сохраняет ввод при ошибке/конфликте, не показывает ложное сохранение, блокирует двойную отправку. После конфликта отдельная кнопка загружает актуальную карточку и явно сообщает о сбросе правок. На смене сотрудника/филиала компонент размонтируется, чтения отменяются и запоздалые ответы не возвращают данные прежнего выбора. Поля общей идентичности блокируются для администратора общей карточки; локальные поля доступны.
