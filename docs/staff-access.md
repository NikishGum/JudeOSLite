# Сотрудники: карточка доступа Б

20.10.2026, [#215](https://github.com/NikishGum/JudeOSLite/issues/215).
Выбранный заказчиком [прототип65acf6d](https://github.com/NikishGum/JudeOSLite/tree/65acf6df74d9204b3385162682b74de4be5ad65c/design-system/prototypes/staff)
перенесён в React на существующие Go/PostgreSQL/API. Один реестр, совмещаемые роли,
филиал и роль фильтруются в одном назначении. Остальные разделы/оболочка PRIDE сохранены.

## Управление

1. Откройте «Сотрудники», найдите имя или логин. Фильтры роли, филиала и состояния
   независимы от выбора адресата. На ПК карточка рядом; на телефоне откройте строку,
   вернитесь через «К списку сотрудников» — фильтры, позиция и фокус сохранятся.
2. «Добавить сотрудника»: новый аккаунт с первым филиалом и ролью. Владелец может
   выбрать существующий аккаунт и добавить одно назначение без нового аккаунта.
   Для аккаунта родителя используйте явный поиск по имени/логину в этой форме;
   до назначения он не появится в списке сотрудников, семейный доступ сохранится.
   Администратор создаёт только trainer в разрешённом действующем филиале.
   Занятый логин требует исправления; автоматического присоединения нет.
3. «Изменить данные» меняет имя/логин. «Сменить пароль» завершает прежние сессии.
   Пароль 12–128 байт, передача вручную лично/по защищённому каналу. Пароль не
   возвращается API, не хранится в storage/истории и очищается после попытки отправки.
4. «Снять назначение» убирает одну роль в одном филиале. Остальные роли и история
   остаются. После последнего назначения рабочие разделы недоступны, аккаунт остаётся
   включённым. Отдельный семейный доступ смешанного аккаунта этим действием не снимается.
5. «Отключить весь доступ» запрещает вход и завершает все сессии этого аккаунта,
   включая семейный кабинет. Назначения сохраняются. Включение требует нового входа;
   старые сессии не восстанавливаются. Будущие занятия автоматически не меняются.

После операции остаётся выбран тот же человек. Если фильтр исключил его из списка,
это подписано в карточке; следующий сотрудник автоматически не выбирается.
Ошибка сохраняет несекретный ввод, конфликт версии требует явной загрузки данных.
Отмена защищает черновик и ничего не отправляет. Во время записи повтор/переход
блокируются. Если запись прошла, но перечитывание не удалось, это отдельное сообщение;
новые действия заблокированы до успешной загрузки.

## Состав и согласованное чтение

`GET /api/staff-directory` → `{staff, clubs, canAssignExisting}`. В одном
`REPEATABLE READ READ ONLY` snapshot повторно проверяются actor/session, читаются
доступные филиалы, версии аккаунтов, role+club назначения и разрешённые действия.
Фиксированное число запросов, без отдельных запросов на каждого человека/филиал.
Ответы `no-store`. Родитель и trainer без administrator-роли получают403.

`staff[]`: `id, login, displayName, disabled, version, canManageAccount,
assignments[]`. Назначение: `clubId, clubName, role, archived, canRevoke`.
`clubs[]`: `id, name, archived`. `canAssignExisting` только owner.

Сотрудником считается non-owner с текущим `staff_club_roles` либо с сохранённым
кадровым событием `staff_user`: `administrator_created`, `administration_updated`,
`trainer_created`, `trainer_assignment_created/revoked`,
`administrator_assignment_created/revoked`. Аудит кадровых API сохраняет бывших
сотрудников после последней роли. Тот же predicate применяется к legacy
`GET /api/staff` и `/api/trainer-accounts`. Обычные parent-only записи, включая
отозванные семейные связи, в реестр не входят. Staff+parent остаётся сотрудником,
семейные сведения/связи в карточку не выдаются. Прямое неаудированное удаление ролей
SQL вне API не является поддерживаемым кадровым процессом.

Owner видит сеть. Admin видит только trainer-назначения своих administrator-филиалов,
включая архивные для чтения/отзыва; чужие роли, филиалы и их количество не выдаются.
`canManageAccount` разрешён локальному admin только для единственного назначения
trainer в его действующем филиале, без `family_access`. Любая дополнительная роль,
филиал или родительская связь сохраняет управление общим аккаунтом владельцу.
Owner-аккаунты в обычном реестре отсутствуют и не назначаются/не отключаются этими API.

`GET /api/staff-candidates?query=...` — отдельный явный поиск только owner:
3–100 символов имени/логина, буквальный поиск без wildcard-семантики, максимум30
результатов, уточнение запроса при достижении лимита. Возвращает `StaffCard[]` из
того же согласованного read helper, включая parent-only, без семейных сведений.
Поиск не меняет роли и не добавляет человека в реестр. Только подтверждённый
owner выбор ID + существующий endpoint назначения переводит аккаунт в staff+parent;
семейные связи, логин и пароль сохраняются. Admin/trainer/parent не получают lookup.
Устаревшие ответы поиска отменяются при смене текста/способа/закрытии формы.

## Запись и совместимость

Существующие операции не дублируются:

| Сценарий | API |
| --- | --- |
| Новый trainer + первая роль атомарно | `POST /api/clubs/{clubId}/trainers` |
| Новый administrator + первая роль атомарно | `POST /api/staff` с одним `clubIds` |
| Данные/disable владельцем | `PUT /api/staff/{id}/account` |
| Пароль владельцем | `POST /api/staff/{id}/password` |
| Локальные данные/пароль | `PUT …/trainers/{id}/account`, `POST …/trainers/{id}/password` |
| Выдать trainer | `POST /api/staff/{id}/trainer-assignments` |
| Снять trainer | `POST /api/clubs/{clubId}/trainers/{id}/revoke` |

Добавлены owner-only точечные операции:

| Запрос | Вход/результат |
| --- | --- |
| `POST /api/staff/{id}/administrator-assignments` | `{clubId, version}` →200 `{status:"ok"}` |
| `POST /api/staff/{id}/administrator-assignments/revoke` | `{clubId, version}` →200 `{status:"ok"}` |

Они меняют только administrator в одном филиале, сохраняют trainer и все остальные
назначения. Валидный повтор с актуальной версией — no-op без нового аудита/version;
устаревшая версия409. Новый архивный филиал409; отзыв архивного разрешён. Некорректный
UUID/версия/неизвестные поля400; owner-target404, non-owner actor403. Legacy bulk
`PUT /api/staff/{id}` остаётся совместимым и сохраняет trainer-роли.

Запись использует прежний `trainerTransaction`: повторные live actor/session/role
проверки под блокировками, target `staff_users FOR UPDATE`, version и club lifecycle.
Создание аккаунта+роли, изменение и audit атомарны; credential/disable триггеры
отзывают сессии в той же транзакции. Новые audit действия содержат только
actor/target/club IDs, assigned/version — без ФИО/логинов/паролей/семейных сведений.
Дубли логина, конкурентные версии и сбой аудита не дают частичной записи.
Новых таблиц/миграций, ролей, auth-сервисов или отправки приглашений нет.
