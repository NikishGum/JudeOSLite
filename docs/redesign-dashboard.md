# RD-05: главные экраны на разрешённых данных

14.10.2026 · [#187](https://github.com/NikishGum/JudeOSLite/issues/187).
Режим Impeccable — Operate. Визуальная основа — существующая
[Working Panel](../design-system/prototypes/dashboard/DESIGN.md),
[PRIDE](../DESIGN.md) и оболочка RD-01. Статический прототип, глобальная
дизайн-система, API посещаемости и миграции не изменяются.

## Композиция и реальные роли

Владелец получает период/группу, четыре итога закрытых журналов, сравнение
филиалов, сегодняшний день, незавершённые и разрешённую историю.
Администратор — ближайшее занятие рабочего контекста, полные счётчики,
группы, день и открытые журналы. Trainer-only — назначенное занятие,
продолжение отметок, свои группы и свои занятия; без реестра сети/истории/отчёта.
На ПК обзор и день рядом; на телефоне занятие раньше счётчиков, а день раньше
групп и истории. Основное действие проверяется в первом экране 390×844/320×780,
включая нижнюю навигацию и обычный заголовок. Длинный контекст переносится;
для меньшей высоты остаётся обычная прокрутка.
В ближайшем занятии группа, статус, время и дата стоят перед основным действием;
имя тренера/«Ваше занятие» и прогресс — после него. Это сохраняет контекст
решения и доступность всей кнопки над нижней навигацией в WebKit на 320 px.

Приоритет RD-01: owner → administrator → trainer. Для выбранного филиала
учитываются его живые назначения. Без выбранного филиала administrator-home
показывает только администрируемые филиалы; trainer-home — разрешённые ему
филиалы. Если администратор другого филиала выбирает свой trainer-only контекст,
получает trainer-home. Многоролевой аккаунт получает «Продолжить отметки» только
при живой trainer-роли и actual trainer ID конкретного занятия.
Переключателя роли и preview controls в production нет.

## Даты, ближайшее и порядок

`GET /api/dashboard?clubId=UUID` вычисляет один `readAt` на сервере.
`clubs[].today` — дата этого момента в **текущем timezone каждого филиала**.
Сегодняшнее занятие попадает в блок по дате его `starts_at` в текущей зоне
филиала. У каждого филиала показаны собственные дата и зона; у каждого занятия
— дата/время в **сохранённом timezone занятия**. Изменение зоны филиала не
переписывает историческую дату сеанса. `branchDate` и `date` могут различаться.

Ближайшее: сначала `open` в разрешённом scope, даже если журнал начат раньше
сегодня; затем `planned` с датой начала в текущей зоне филиала не раньше его
сегодня. Среди равных приоритетов — `starts_at`, затем ID. Время ранее текущего
момента в сегодняшнем дне не убирает ещё не открытое плановое занятие.
`closed`, `cancelled` и superseded не становятся текущей задачей.
Trainer-only видит только фактические назначения своего ID. Администратор
видит доступные занятия рабочего филиала. Списки дня/открытых упорядочены
по абсолютному началу и ID; дата и timezone каждой строки видимы явно.

Обзор владельца переиспользует `reportPeriod`, `useAttendanceReport`,
`AttendanceSummary` и `ReportComparison` из [RD-04](redesign-reports.md).
Начальный период — месяц по сегодня; быстрые периоды определены по Минску,
обе границы включительны. Отчёт считает день в сохранённой зоне каждого
занятия, как API v1. Это подписанная граница сетевого отчёта, независимая от
локального «Сегодня». Свой диапазон восстанавливается в пределах монтирования.
Выбор строки сравнения/группы меняет UUID контекста **отчёта**, который подписан
над итогами. «Вернуться к контексту главной» восстанавливает рабочий фильтр.
Все показатели/групповые сравнения остаются в полном отчёте; компактная главная
не вводит другой расчёт процента.

## Один минимальный read endpoint

`backend/internal/dashboard` читает существующие таблицы без новых бизнес-сущностей,
миграций, материализованных отчётов или кеша. Сервер повторно проверяет и удерживает
live actor/session/назначения/активные филиалы под `FOR SHARE`. Чтение имеет одну
`REPEATABLE READ` транзакцию: счётчики и ограниченные списки относятся к одному
снимку. Новый запрос видит новые подтверждённые записи. Клиентские role/actor
параметры не дают доступа; неизвестный/чужой/архивный выбранный филиал — 404.

| Поле | Точная семантика |
| --- | --- |
| `participants` | Все неархивные локальные карточки доступного manager-scope, без фильтра/страницы; `null` у trainer-only. Это карточки филиалов: общая личность в двух филиалах даёт две карточки, а не уникальное число людей сети. |
| `groups` | Все активные доступные группы; trainer-scope соответствует назначению правила/actual сеанса в существующем API занятий. |
| `today` | Полное число занятий локального дня, включая видимые closed/cancelled, без superseded. |
| `open` | Полное число доступных open, включая незавершённые прошлых дней. |
| `roster`, `marked` | SQL-агрегат замороженного снимка, а не отдельное чтение каждого журнала. Planned не выдаёт пустой ещё не созданный снимок за число ожидаемых участников. |
| `groups[].members` | Текущий датированный состав на локальную дату филиала, без архивных локальных карточек; он не изменяет замороженный журнал. |

Список дня ограничен 12 строками, open — 6, групп — 8. Полные счётчики считаются
отдельно от LIMIT; при ограничении UI пишет «Показано N из M» и предлагает раздел
нужного филиала. Нет подсчёта длины страницы как общего реестра. Ответ `no-store`
содержит только нужные сводные поля, названия/IDs; без контактов, рождения,
индивидуальных отметок, private payload или причин коррекций.

Последние изменения используют прежний public envelope `/api/audit/events`:
до пяти последних из первой разрешённой страницы, без заявления полного числа
событий. Owner/admin scope проверяет существующий аудит; trainer блок не получает.
Имена актуальные, время аудита по Минску; полный просмотр — прежняя история.

## Переходы и актуальность

Обычные ссылки [RD-03 `sessionHref`](redesign-training.md) передают club/group/
session IDs, фактическую дату и journal mode. Они поддерживают reload/back/forward,
модифицированный клик и существующий beforeunload guard. Planned открывает нужное
занятие; снимок создаётся только после отдельного подтверждения тренера. Ссылка
группы у manager ведёт в detail группы по UUID, у тренера — в календарь её занятий.
Ссылки филиала ведут в его реальный рабочий контекст.

«Добавить участника · филиал» ведёт в `/clubs/:id/participants?detail=new` и сразу
открывает пустую форму. `new` допускается только для participants; UUID detail
групп и существующих карточек сохранены. В URL нет введённых данных. Для сети/
нескольких филиалов предлагаемый филиал назван в действии; сменить его можно
существующим выбором филиала. Старые формы/права/dirty guard сохраняются.

Главная, отчёт и история — независимые read-блоки. Ошибка одного не выдумывает
нули и не очищает здоровый независимый блок. При загрузке/сбое старый ответ блока
скрывается, retry сохраняет контекст. Новое монтирование после состава/архива/
отметки/закрытия/коррекции читает сервер; `attendance-changed`, focus/visibility
и 30 секунд в видимом окне обновляют чтение. Никакой скрытый отчёт ради кеша не
монтируется. Abort/request key, общий auth generation и NavigationBoundary
user/owner/назначений/филиала не пропускают поздний ответ прошлого scope.
401 очищает сессию, 403/404 запускают повторную проверку доступа и очистку
приватного DOM. Офлайн-очереди, synthetic fallback, жёстких имён/чисел/дат нет.
