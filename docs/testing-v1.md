## Автоматическая регрессия

Из корня с Docker/Compose, Node 24.19, Python Playwright 1.62:

```sh
cd frontend
npm ci
npm run build
cd ..
docker build -f deploy/Dockerfile -t judeoslite:ci .
python3 -m pip install playwright==1.62.0
python3 -m playwright install --with-deps chromium webkit
python3 frontend/e2e/pwa_v1.py
PWA_BROWSER=webkit python3 frontend/e2e/pwa_v1.py
```

В managed cloud читать skill окружения; Docker build получает CA через
`--secret id=proxy_ca,src="$CODEX_PROXY_CERT"`. `CHROMIUM_PATH` позволяет выбрать
установленный Chromium. Два движка запускаются последовательно: используется
loopback :18081. Скрипт создаёт и в finally удаляет только уникальные pwa161-*
network/app/db; PostgreSQL 18.6 browser161, синтетический owner и пароль.
Рабочие VPS/БД не используются. CI исполняет обе регрессии после production build.

В WebKit сетевые отказы внедряются в отдельный trainer-context с
`service_workers=block`: Playwright routing не перехватывает запросы страницы,
контролируемой worker. Owner/admin проверяют настоящий worker/cache/update.
Задержка обработки ответа для late report/update guard использует временную
обёртку fetch **в тесте**: сервер действительно выполняет запрос, SQL подтверждает
запись, клиент получает ответ после явного освобождения. Production-код не меняется.
Offline reload в Chromium проверяется через browser offline; WebKit проверяет
публичную оболочку при настоящей остановке disposable app с последующим restart
и readiness. Его `set_offline` для navigation завершается внутренней ошибкой до
worker fallback, поэтому этот сигнал не используется как доказательство работы
Safari. Offline mark в отдельном trainer-context проверяется обоими движками.

Путь UI → Go HTTP API → PostgreSQL → UI:

- Owner готовит филиал/администратора; admin через UI создаёт группу, тренера,
  пять участников с одинаковым семейным телефоном и начальным составом.
- Admin через формы создаёт weekly (один выбранный день), odd day_parity,
  date_list (две даты) и once (без rule). Python независимо перечисляет даты;
  предпросмотр и реальные API-сеансы совпадают. Double submit даёт один POST.
- Исторический сеанс на сегодня создаётся в **disposable SQL fixture**, чтобы
  journal flow не зависел от времени запуска CI. Четыре UI-расписания создают
  настоящие будущие сеансы; этот исторический сеанс не выдаётся за созданный UI.
- Trainer открывает снимок пяти карточек: A present, B unknown, C illness,
  D excused; E становится close_default/unknown. Проверены причины, отмена
  панели/Escape/focus cycle, двойной тап, задержка, явный offline, отказ до commit,
  потеря ответа после commit и identical retry без второго audit, reload открытого
  журнала с продолжением с E. Closed — без кнопок записи.
- Admin исправляет C на present с причиной. Owner видит 1 closed, 2 present,
  3 absent, 40%; причины unknown=2, illness=0, excused=1.
- Отмена настоящего open сеанса сохраняет пять unmarked без defaults, запрещает
  запись. Live отзыв trainer-роли блокирует сохранение и очищает снимок.
- 320/390/1280 px, короткая панель 320×480, цели ≥44 px, отсутствие overflow/JS
  errors. Manifest/icons, Chromium installability, static-only Cache Storage,
  offline публичная оболочка/отсутствие API fallback, смена сотрудника/две вкладки,
  expiry/pagehide/pageshow, две реальные сборки/waiting/save guard/другая вкладка.

Скрипт печатает JSON с настоящим engine/version, counts/report и
physicalInstallation=NOT TESTED. Снимки `/tmp/pwa161-{engine}-{screen}-{width}.png`
содержат только disposable synthetic данные. [Контракт PWA](pwa-v1.md).

Пароли задавать/вводить в защищённой CRM, не в Git/чате.
Перед началом записать дату, устройство, ОС, полную версию браузера и
`https://test.judopride.tech/release.json` → sha. При обновлении release между
проверками записать оба SHA. Использовать только тестовые карточки в отдельной
группе `QA164`; не менять существующие группы/участников. **Полный путь 1–6
достаточно выполнить один раз на ПК Chrome.** На iPhone и Edge выполнить
шаги 7–10: ввод/размеры/панель/сеть, установка и повторный запуск. Для панели и
проверки связи admin создаёт отдельный once сегодня с будущим временем для
каждого устройства; не закрывать его до контрольного отчёта основного пути.
После проверки можно отменить дополнительный сеанс через admin UI. Нет требования
четырежды создавать филиал, аккаунты и пять участников.

1. Owner создаёт тестовый филиал/администратора (либо выбирает уже выделенный
   синтетический филиал). Выйти. Admin входит и создаёт тестовую группу, тренера
   и пять участников `QA164 A`–`QA164 E`: рождения 01.01.2010, вступление и
   включение в группу сегодня, один контакт `+375291234567`. Проверить нативный
   ввод даты/телефона, клавиатуру, поиск, сохранение и повторное открытие карточки.
2. Admin создаёт четыре расписания этой группы с разным временем, чтобы избежать
   пересечения: weekly со следующего дня, odd parity со следующего дня,
   date_list на две будущие даты, once **сегодня с будущим временем**.
   Сверить предпросмотр с календарём; once станет основным тестовым журналом.
   Если сегодня уже невозможно выбрать будущее время, продолжить на следующий
   день. Проверить все формы в портретном/альбомном положении и масштаб текста;
   на ПК также сузить окно. Горизонтальной прокрутки быть не должно.
3. Выйти, войти trainer. Открыть сегодняшний once, подтвердить снимок пяти.
   Дважды быстро нажать present на A: ровно одна отметка/переход. На B открыть
   панель и отменить: записи нет; выбрать unknown. C — illness, D — excused.
   Перезагрузить открытый журнал: продолжение с E, предыдущие отметки сохранены.
4. На E выключить сеть до нажатия present: нет сообщения об успехе/перехода,
   карточка остаётся E. Вернуть сеть, обновить журнал — E ещё unmarked.
   Разрыв сети **во время** сохранения проверить отдельно на дополнительном
   тестовом сеансе: после ошибки нет обещания успеха; reload/retry согласует
   состояние с сервером (запрос мог успеть записаться). Не требовать rollback
   уже принятого сервером запроса. Если воспроизвести разрыв не удалось —
   отметить NOT RUN, не PASS.
5. Завершить основной once, оставив E unmarked: подтверждение говорит «1»,
   итог E absent/unknown, журнал read-only. Admin исправляет C illness→present
   с причиной `QA164 исправление`. История сохраняет старую/новую отметки и
   авторов. Owner фильтрует **эту группу/сегодня**: 1 closed, 2 present, 3 absent,
   unknown=2/illness=0/excused=1, 40%. Будущие planned считаются отдельно.
6. Admin создаёт дополнительный once сегодня; отменяет с причиной. Trainer
   обновляет список: отмена видна, записи нет. Для отзыва доступа создать ещё
   once сегодня, trainer открывает журнал; admin в другом окне отзывает только
   тестовое trainer-назначение. Следующий save отказывает и скрывает карточки.
   Повторно назначить тестового тренера может owner; историю не удалять.
7. **На каждом из трёх обязательных браузеров (iPhone/Safari, ПК Chrome/Edge):** открыть тестовую карточку участника,
   ввести/сохранить прежние синтетические дату и телефон, перезагрузить и сверить.
   Открыть формы всех четырёх режимов (повторно сохранять правила не требуется).
   Trainer открывает дополнительный сеанс, проверяет панель/отмену; выключить
   сеть перед save — нет ложного успеха/перехода, вернуть сеть/reload.
   Выйти, войти другим сотрудником и перезапустить: прежнего журнала/контактов
   нет. Проверить страницу входа, реестр, четыре формы, карточки, панель с
   экранной клавиатурой/коротким экраном, журнал admin и статистику: цели доступны,
   нижние кнопки не скрыты системной областью, нет горизонтальной прокрутки.
8. **iPhone/Safari:** Поделиться → На экран Домой → Добавить. Закрыть Safari,
   открыть значок с Домой: standalone, правильная сессия/вход, нет подсказки
   установки. Войти/открыть журнал, закрыть приложение и запустить повторно;
   данные перечитаны. Проверить портрет/альбом, safe area выреза и нижней полосы.
   Выйти из PWA, запустить снова: прежний журнал не отображается.
9. **Android/Chrome — отложено, вне текущей приёмки:** меню → Установить приложение / Добавить на главный экран,
   либо штатная кнопка. Убедиться, что открывается standalone PWA, а не только
   вкладка браузера. Закрыть/открыть значок, проверить текущую сессию, журнал,
   offline без ложного сохранения и выход/повторный запуск.
10. **ПК Chrome и Edge отдельно:** выполнить шаг 7 в обоих, полный путь 1–6
    один раз в Chrome; проверить Tab/Shift+Tab/Escape/Enter, узкое и широкое окно.
    Установить через адресную строку/меню, закрыть/открыть окно приложения,
    проверить текущую сессию и выход. Если конкретная установка недоступна,
    записать точный результат и причину.

### Локальные дефекты и исправления

На исходном 88edc2e Node24.19/frontend и arm64 production Docker прошли;
неизменённый E2E **FAIL** на bundled Chromium151.0.7922.34, Chrome154.0.8037.98,
Edge155.0.4283.45 (D1) и Mac Playwright WebKit26.5 (D2, затем D3 в диагностике).
Диагностические копии с обходами не считаются PASS исходной регрессии.

- **D1:** cache_check требовал один кеш до активации waiting B. Два versioned
  static-only кеша в этот момент корректны. Регрессия теперь удерживает A
  дополнительной вкладкой, проверяет точные кеши A/B до explicit update,
  затем controller activation/reload и единственный B. Проверки приватности
  сохраняются для обоих кешей.
- **D2:** native appearance в Mac WebKit давал select 24 px. Select использует
  appearance:none и стрелку в CSS с цветом PRIDE; настоящий HTML select,
  подписи и нативный выбор опций сохраняются, применяется цель ≥44 px.
- **D3:** нативный Tab от средней кнопки мог уходить на BODY. ActionSheet
  явно переводит фокус при каждом Tab/Shift+Tab, включая heading/wrap/disabled;
  Escape и возврат фокуса сохранены. E2E проверяет каждую кнопку в обоих направлениях.

Исправления проходят Cloud/Linux регрессию и CI; **их результат на macOS ещё
требует повторного запуска исходных тестов без диагностических обходов**.
После обновления установленной PWA повторить select/date/contact, panel
Tab/Shift+Tab/Escape на Mac и native select/panel/relaunch на iPhone. Старые
physical PASS относятся к 88edc2e, не автоматически к изменённому CSS/focus.

Первый main CI a358b87 (38400282537) прошёл Chromium, но остановился в WebKit
на disabled выборе начальной группы. Последующий локальный прогон остановился
на открытии формы расписания; следующий полный WebKit-прогон прошёл. Эти
остановки не объявлены устранённым продуктовым дефектом без причины/повторения.
При следующем таком FAIL скрипт выводит состояния loading/error/busy, disabled
select/options и последние HTTP status/request failure для disposable admin UI.
Проверка не ослаблена: нет force, автоматического retry или зачёта diagnostic
обходов. Итоговый успешный CI нового SHA и первоначальный FAIL сохраняются в issue.
