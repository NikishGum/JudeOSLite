Общая оболочка учитывает safe area со всех сторон и короткий экран; текст/поля/кнопки переносятся на 320 px. Основные цели от 44 px, тренерские отметки/причины от 56 px. Фокус видим, после смены входа фокусируется заголовок; нижняя панель V1-10 сохраняет modal/focus cycle. Поля даты/времени не переполняют узкую колонку. Загрузка, пустые списки, ошибки и явный повтор сохраняются в предметных разделах; фильтр групп отдельно показывает пустой результат.

## Установка и запуск

На production HTTPS доступен `/manifest.webmanifest`: id/scope/start_url `/`, имя PRIDE, `display: standalone`, русский язык, фон/акцент PRIDE. PNG 192/512 и отдельная maskable 512 получены из исходной эмблемы без перекраски/растяжения. Maskable помещает эмблему в центральные 75% белого квадрата; исходник 256 px увеличен для размера 512, нового векторного оригинала нет. Apple touch icon и viewport-fit=cover подключены в HTML.

«Установить PRIDE на устройство» доступно и до входа. iPhone/Safari: Поделиться → На экран Домой → Добавить. Android/Chrome: меню → Установить приложение / Добавить на главный экран; при `beforeinstallprompt` появляется штатная кнопка. ПК Chrome/Edge: установка из адресной строки. В standalone подсказка скрыта. Каждый запуск сначала проверяет настоящую серверную сессию: устанавливаемая оболочка не содержит сотрудника или журнал. Установка не предоставляет доступ и не заменяет интернет.

Service worker регистрируется только в production build; для разработки используется обычный Vite proxy. Требуются HTTPS или доверенный браузером loopback origin. `sw.js`/manifest/HTML сервер отдаёт с no-cache; `/assets/` — immutable.

## Кеш и сеть

`frontend/pwa-build.ts` создаёт `/assets/pwa-shell-HASH.html` из публичного build-time index.html и `/sw.js`. Версия кеша `pride-shell-HASH` зависит от имён хешированных bundle outputs, HTML, worker template и manifest. Allowlist содержит только конкретные версии JS/CSS/fonts/logo/icons и этот HTML. Установочный fetch без credentials; Cache Storage никогда не дополняется ответами во время работы.

Worker обрабатывает только same-origin GET из allowlist без query и навигации `/`, `/login`, `/clubs/{id}`. `/api`, `/api/*`, другие пути/методы/origins проходят в сеть; JSON/API/личные данные/CSRF/cookie/очереди отсутствуют в кеше. Навигация network-first с no-store, при сетевом отказе — только публичный versioned shell. Ответы навигации не сохраняются. Ошибка pre-cache удаляет незавершённый новый кеш и не активирует новую версию; activation очищает предыдущие кеши только namespace PRIDE.

Без сети виден общий banner: операции недоступны, сохранение не обещается. `navigator.onLine` дополняется событиями фактического сбоя/ответа API, поскольку наличие сетевого интерфейса не гарантирует доступ к серверу. Общий API-клиент блокирует отправку изменений при `navigator.onLine=false`; неожиданная потеря связи обрабатывается существующими ошибкой/повтором без перехода/ложного успеха. Нет localStorage/IndexedDB с журналом, offline queue, Background Sync или автоматического повтора записи. После офлайн-перезагрузки нет личного экрана, есть вход/ошибка доступа и «Проверить подключение и доступ»; после восстановления связи явный повтор читает сервер.

## Сессия и обновление

Успешный выход/401 размонтирует предметные компоненты, очищает выбранный филиал, пароль, CSRF и личные данные. Успешные вход/выход отправляют по BroadcastChannel только неперсональное `changed`; соседние вкладки синхронно очищают DOM и перечитывают me. При отсутствии BroadcastChannel остаются штатные focus/30-second проверки сессии. Запоздалые ответы прежнего поколения auth не возвращают прежние данные. `pagehide` синхронно убирает личные компоненты до back/forward snapshot; persisted `pageshow` перечитывает сессию. Персональные данные не сериализуются в client storage.

Новая версия остаётся `waiting`: install не вызывает skipWaiting. Обновление проверяется при регистрации, возврате видимой страницы и восстановлении сети. Пользователь видит явную кнопку и предупреждение сохранить введённые данные. Общий счётчик мутаций охватывает fetch и чтение тела ответа (в том числе login/logout/preview); пока счётчик ненулевой, кнопка disabled. Обработчик повторно синхронно проверяет счётчик, закрывает старт новых мутаций и просит активировать worker. Только инициировавшая вкладка перезагружается по controllerchange; другие вкладки продолжают свои сохранения без автоматической перезагрузки. Если активация не подтвердилась за 15 секунд, блокировка снимается и предлагается повтор.

Несохранённый ввод не хранится между явными перезагрузками; перед обновлением нужно сохранить/отменить форму. Общий счётчик защищает запрос, уже отправленный через API-клиент; обновление не является автоматическим сохранением формы. На reload снова проверяется текущая серверная сессия, журнал загружается из БД.

## Проверка и воспроизведение

Из корня с Docker/Compose, Node 24.19 и Python Playwright 1.62/Chromium:

```sh
cd frontend && npm ci && npm run build
cd ..
docker build -f deploy/Dockerfile -t judeoslite:ci .
python3 frontend/e2e/pwa_v1.py
```

В managed cloud перед сборкой прочитать правила окружения; Docker build использует CA secret `--secret id=proxy_ca,src="$CODEX_PROXY_CERT"`. Обычный build использует системное доверие. Если Chromium отсутствует, `python3 -m playwright install --with-deps chromium`; CHROMIUM_PATH задаёт установленный бинарник. CI выполняет ту же PWA-регрессию после production image build.

Скрипт сам создаёт/удаляет уникальные `pwa161-*` Docker network/контейнеры и PostgreSQL 18.6 browser161, публикует приложение только на loopback :18081, интерактивно создаёт synthetic owner. Рабочие БД/серверы не используются. Второй frontend build создаётся в temporary directory с изменённым публичным title; обе реальные сборки по очереди копируются в disposable app. Все данные/пароли синтетические. При запуске порт 18081 должен быть свободен.

Проверяются UI → API → PostgreSQL → UI: admin создаёт группу/тренера/участника с начальным составом и разовое расписание; trainer открывает настоящий снимок, повторяет неотправленную offline mark и закрывает; admin исправляет с причиной, owner видит исправленные SQL суммы. Все три роли/вход/формы/карточки/коррекция/таблица на 320/390/1280 без горизонтального overflow и JS errors, размеры целей; нижняя панель на 320×480, фокус и Escape без записи. Chromium DevTools проверяет manifest/installability и размеры иконок в обычном persistent profile; incognito намеренно не используется для installability. Проверены install prompt/standalone сигналы (эмуляция), публичная offline оболочка, отсутствие API fallback и личного кеша, logout/смена сотрудника в двух вкладках, expiry журнала и pagehide/pageshow. Две сборки: ожидание обновления, disabled при задержанном подтверждении записи, успешный reload/новая сессия/очистка старого кеша, сохранение другой вкладки во время activation. Снимки `/tmp/pwa161-{экран}-{320,390,1280}.png`.

Go formatting/vet/build и полный PostgreSQL `go test -race ./...`, production Docker, Compose clean/rerun/restart/readiness/непубличная БД также проверяются. Итоговые SHA, CI, доставка в main и статус — в live issue. **Реальные iPhone/Safari, Android/Chrome, Chrome/Edge и установка на физические устройства остаются V1-16/#164; production HTTPS/предметное восстановление — V1-17/#165.** Chromium и имитация standalone не заменяют эту приёмку.
