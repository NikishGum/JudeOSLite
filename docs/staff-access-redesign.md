# Сотрудники: выбранная карточка доступа

20.10.2026, прямое решение заказчика в чате «Сотрудники — два UX-прототипа».

Для основного веб-приложения выбран **вариант Б — «Карточка доступа»**. [Issue #215](https://github.com/NikishGum/JudeOSLite/issues/215) фиксирует реализацию React/Go/API и критерии готовности; при создании Todo без исполнителя. До запуска реализации задачу требуется включить в штатный реестр/план, после чего занимать через очередь по docs/collaboration.md. Создание issue не резервирует работу.

Подтверждено:

- Единый список сотрудников; trainer/administrator — совмещаемые роли, без вкладок «сотрудники / тренеры».
- ПК: список и карточка рядом; телефон: карточка с явным возвратом и сохранением фильтров.
- Основные операции: создать сотрудника/выдать доступ, сменить пароль, снять назначение или отключить весь доступ. Последствия различаются до подтверждения.
- Если текущих backend-возможностей недостаточно для согласованного UI, дополнить их в рамках того же issue, сохраняя права, сессии, версии и историю.

Референс: [prototype commit 65acf6d](https://github.com/NikishGum/JudeOSLite/tree/65acf6df74d9204b3385162682b74de4be5ad65c/design-system/prototypes/staff). Снимок актуального main для анализа API: `19f6d13270353906a529cce234e53eac12efdefc`. Существуют разделённые staff/trainer DTO и операции; не утверждать, что смена пароля или отзыв отсутствуют. Проверить согласованную выдачу всех назначений и корректный состав реестра после появления parent-only/shared аккаунтов (#201).

Состав конкретных API-изменений определяется по актуальному коду при реализации, а не по упрощённому моковому JS. Включение parent-only пользователей в сотрудники только по признаку non-owner недопустимо; бывшие сотрудники без назначений должны остаться управляемыми. Глобальная дизайн-система и текущая оболочка сохраняются.

Выбор Б подтверждён. Production-реализация, проверки реальных API и её приёмка пока не выполнены; это отдельные результаты #215.
