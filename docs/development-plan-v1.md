## Порядок и первый рабочий результат

**Подтверждённый приоритет заказчика:** быстро получить работающую версию, существенно не усложнять backend и сохранить основу для масштабирования. Применяем это к порядку реализации и границам задач.

Инженерное предложение: один Go-сервис, одно React-приложение, PostgreSQL, один HTTPS-origin и Compose. Операции пишутся прямо в предметных пакетах с явным SQL. Для сложной финансовой операции — одна транзакционная функция; для простого чтения — небольшой обработчик. Контракт отдельной операции фиксируется в её API-задаче; отдельные controller/service/repository и задача на каждый файл не обязательны. Небольшие интерфейсы нужны только на реальных внешних границах БД, iPay и времени.

Масштабирование поддерживают club_id и серверные права, стабильные ID, миграции, индексы под запросы, датированная история, безопасные повторы и независимые предметные пакеты. Отдельные сервисы, брокер, CQRS, универсальный конструктор форм, универсальный repository, плагинная платформа, event sourcing, динамические отчёты и аналитическое хранилище в v1 не требуются. Сначала измерить реальную проблему; не закладывать инфраструктуру ради гипотетической нагрузки.

**Первый рабочий технический срез — QA-03:** на тестовой установке создать клуб, тренера, группу и участников; задать расписание; открыть занятие; отметить карточки с телефона; завершить журнал и перечитать сохранённые результаты. Справки, массовый импорт, деньги и общий обзор добавляются следующими результатами. Это последовательные результаты разработки внутри полной v1, а не согласование частичного финансового запуска клуба. Рабочий запуск сотрудников всего клуба остаётся после итоговой приёмки.

| Этап | Результат | Предшественники и переход |
| --- | --- | --- |
| E0 | Уточнённые небольшие контракты и пакет внешних условий | DEC-01/02/03 доступны сразу; Excel/iPay и финансовый переход — отдельные ветви, не общий барьер |
| E1 | Вход, клубные права, оболочка и тестовый HTTPS-запуск | DEC-01/03; вход/выход/отзыв проверены, секреты не выдаются |
| E2 | Карточки и группы | E1; создание атомарно, другой клуб недоступен; архив/перевод могут идти после первого демонстрационного сценария |
| E3 | Занятия и карточки тренера | Минимальная ветвь E2 + DEC-02; QA-03 демонстрирует первый результат; ATT-12 закрывает риск истории/гонок |
| E4 | Отдельные справки и повторяемый импорт | Реестр/группы; медицинская часть не ждёт Excel; реальный импорт ждёт DEC-06 и согласованных остатков |
| E5 | Цена, пауза, начисления, корректировки и объяснимый остаток | DEC-04 и реестр; PAY-01–04 добавляют минимальный ledger, без рабочего iPay; FEE-14 ждёт DEC-09 |

OPS-01 находится в E1, чтобы тестовый телефонный запуск не переносился на конец. Финансовые задачи с внешним условием можно готовить на синтетических данных, но нельзя объявлять их рабочим подключением.

## Расхождения и инженерные уточнения

1. Ранее T12 содержала только unmarked/present/absent/sick и change_reason. Новый выбор трёх причин требует отдельного absence_reason. Схема 1.2/диаграммы 1.1 дополнены предложением: absent + unknown/excused, sick + illness; present/unmarked + NULL. DEC-02 проверяет совместимость БД/API/UI; это техническое представление, не дополнительное требование заказчика.
2. Первое предложение оставлять неотмеченных отдельно после закрытия заменено последним ответом заказчика. До завершения unmarked не отсутствие; при завершении одна транзакция создаёт absent/unknown для оставшихся и закрывает журнал. Исправление администратором не открывает его заново.
3. Раннее ограничение UI болезни обязательным концом снято: у обоих видов конец может быть неизвестно. NULL не использовать как гарантированный бессрочный медицинский допуск и не превращать в автоматический запрет/разрешение участия.
4. Остановка/возобновление оплаты определяется выбранными месяцами, а не датой joined_on/archived_at. Предложено использовать разрыв fee_terms. Неполный месяц предлагается отражать обычным начислением и отдельной корректировкой, с аудитом; DEC-04 фиксирует контракт.
5. Теперь обычная оплата только текущего месяца и точная. Ledger оставлен для целостности, сторно и финансовых исключений; это не разрешение предоплаты или произвольного ручного «оплачено». Фактическое поступление не удалять при ошибке разнесения.
6. T19 раньше допускала NULL target_month. Для выбранной точной оплаты текущего месяца при принятом старте он обязателен. Минимальное предложение: charge определяется по club_membership_id + target_month + kind=monthly_fee, защищённым существующим UNIQUE; сумма фиксируется в attempt. При результате за новый месяц цель не меняется. Дополнительная таблица счетов, target_charge_id и универсальный механизм политик не нужны этому сценарию. PAY-02/08 проверяют этот контракт; неизвестный результат хранится как событие quarantine, а не принятая попытка без цели.
7. Срок «до 7-го», тарифы/число залов и формат iPay из исследовательской базы не превращены в действующие настройки. Просрочку, реальные группы и коды вводить только по подтверждённым данным.
8. Большая историческая архитектура не должна превращаться в предварительное создание всех пакетов/таблиц/слоёв. Минимальный срез добавляет только необходимые данные; тяжёлые ветви реализуются по зависимостям. Отдельный обработчик iPay остаётся внутри того же Go-сервиса.
9. Схема допускает неизвестный конец болезни, но не восстанавливает исторический статус участника из одного текущего T06.status. Для показателя «действующие участники по месяцам» DEC-05 должен определить срез: например, текущая численность отдельно от посещавших за месяц. Если нужен исторический статус членства, отдельно согласовать минимальную историю; не выдавать текущее состояние за прошлое.

## Как читать карточки

Одна карточка — один принимаемый результат; локальная проверка включена. API-задача включает контракт только своей операции: права, запрос/ответ, ошибки, version/request_key, пагинацию при чтении и соответствующий обработчик. Не создавать по три инфраструктурных задачи для каждого простого endpoint. Проверочные задачи выделены для самостоятельного риска истории, прав, денег, импорта и внешнего обмена.

Все пути будущего кода — **предполагаемые области**, не существующие файлы и не инструкция создать их сейчас. XS/S отражают относительный размер, не часы. Если конкретная карточка при реализации требует нескольких самостоятельных результатов/большого изменения, разделить её, сохранив ID исходного результата и обновив зависимые ссылки.

Для каждой UI-задачи обязательны читаемый телефон/ПК, loading/empty/error/success, доступные подписи/фокус, отсутствие двойной отправки и подтверждение сохранения только после ответа сервера. Это часть её результата, не отдельный заключительный проект адаптации.

## Остаточные условия и границы

До внешних материалов неизвестны договорные условия iPay и реальный формат Excel. До согласования перехода неизвестен способ оплаты старых долгов, состав/дата начальных остатков, правила нулевого требования и финансовых исключений. До обзора неизвестны точные формулы временных срезов. Эти неизвестные не маскируются готовыми функциями.

Состав v1 сохраняется: сотрудники трёх ролей, сеть клубов, реестр, группы/расписание/посещаемость, справки, месячные взносы, iPay, импорт, обзор, PWA, VPS/backup. Кабинеты родителей, самостоятельная запись, аренда, гостевая тарификация, мессенджеры/push, диагнозы/сканы, офлайн-очередь, автоматические льготные формулы и бухгалтерская система — вне этого плана.

**Всего:** 8 разделов реализации, 148 небольших задач. Ориентир промпта 80–120 не использован как искусственный лимит: отдельные операции/формы и денежные риски сохранены самостоятельными, без задач «создать папку» и без предварительного построения тяжёлой инфраструктуры.
